REQUIRED DATA SOURCES AND PREPARATION

Four synthetic datasets represent independent hospital systems on four distinct continents:

- Source A: North River Teaching Hospital, Montreal, Canada, North America; TXT format; 9,438 raw records.
- Source B: Berlin Central Clinical Centre, Berlin, Germany, Europe; CSV format; 9,438 raw records.
- Source C: Osaka Metropolitan Medical Centre, Osaka, Japan, Asia; XML format; 9,438 raw records.
- Source D: Cape Meridian Hospital, Cape Town, South Africa, Africa; JSON format; 9,438 raw records.

All hospitals and personal records are fictional. Each source is within the required range of 5,000-10,000 records, and the combined 37,752 records are within the required total of 20,000-40,000. Each source contains related patients, admissions and diagnoses, together with assessments, healthcare professionals, units, unit stays, orders, examinations, radiology reports, procedures, clinical notes, discharge information and ICD-9 dictionary entries.

AI assistance supported synthetic-source preparation, Python implementation and report drafting. The supplied generation prompt requested four hospital datasets satisfying the assignment's source formats, geographic coverage, size limits, hospital content and controlled data-quality problems, using the supplied hospital ER structure. The accompanying Python generation script uses synthetic values, Faker and fixed random seeds. The raw files were subsequently inspected using the Task 1 script, and cleaning decisions were applied through the Task 2 script. AI output was checked against the actual files and processing results rather than treated as automatically correct. Original raw files remain unchanged.

The original source snapshot remains unchanged under uncleaned data/raw. A revised synthetic snapshot is prepared under uncleaned data/raw_with_admission_types by prepare_admission_types.py. This version adds one explicit admission-type attribute to each admission without changing the other record values or the number of records. Tasks 1 and 2 read this revised snapshot and do not modify it during processing.

Admission types are generated synthetic attributes, not clinical facts recovered from admission status, symptoms or other existing values. A fixed seed based on the source and local admission identifier makes their generation reproducible. The simulated Emergency probabilities are 70% for A, 50% for B, 60% for C and 40% for D. These are dataset-design choices, not estimates of national hospital statistics. Run prepare_admission_types.py before the two Task scripts; it reproduces the revised sources from the preserved original snapshot.

Each source uses its own type field and vocabulary:

- Source A: admission_type contains Emergency or Elective.
- Source B: Aufnahmeart contains Notfall or Geplant.
- Source C: admissionType contains 緊急 or 予定.
- Source D: ADM_TYPE contains EMERGENCY or ELECTIVE.

TASK 1: INSPECT AND LOAD THE DATA USING PYTHON

Task 1 loads and inspects the four hospital datasets in the revised synthetic source snapshot using Python. Each source is stored separately in a dictionary, with each entity represented as a list of record dictionaries. Original field names and values are preserved during loading and profiling. No cleaning, standardization, or deduplication is performed at this stage.
The source formats and record layouts are as follows:
Source A — TXT: Files use UTF-8 encoding and the pipe character (|) as the delimiter. Each file represents one entity type. The first logical record contains field names, and subsequent records contain values in the same order as the header.
Source B — CSV: Files use UTF-8 encoding and commas as delimiters. Each file represents one entity type, with field names in the first record. The CSV parser handles quoted values containing commas or line breaks.
Source C — XML: The document has a hospital_dataset root containing entity groups. Each group contains record elements, whose child elements represent individual fields. Root attributes contain metadata and are not counted as entity records.
Source D — JSON: The top-level hospital object contains metadata. The entities object maps entity names to arrays of record objects. Each record object is extracted as one entity instance; metadata and container objects are not counted as records.
The sources contain formatting differences that must be considered during inspection. Source A uses dates in YYYY-MM-DD format, Source B uses DD.MM.YYYY, Source C uses YYYY/MM/DD, and Source D uses DD/MM/YYYY. Field naming also differs: the patient identifier appears as patient_id, PatientNr, patientNumber, and PAT_ID, respectively.
The initial profile reports record counts and exact duplicate counts for each source and entity. An exact duplicate is a complete record identical to another record within the same source and entity. Duplicate counts represent repeated copies beyond the first occurrence. The script also reports field names, inferred data types, missing-value counts, and representative nonmissing values. Type inference examines nonmissing values, while identifier-like fields are labelled as identifiers or codes to indicate that string storage is appropriate.
For profiling purposes, missing values include nulls, empty or whitespace-only strings, and the case-insensitive markers NULL, N/A, NAN, NA, k.A., 未記録, and -. The source-specific missing markers are recognized consistently across fields. The literal text "None" in allergy and medication fields is preserved because it can express a documented absence rather than unavailable information. These rules follow the documented source conventions and are applied without changing the original values during Task 1.
Invalid-value checks identify examples such as impossible dates, invalid times, and numeric measurements outside the script’s documented screening ranges. Leading and trailing whitespace is also flagged. These checks identify potential quality problems without modifying the original records. The numeric ranges are profiling assumptions rather than clinical diagnostic thresholds.
Malformed or unreadable input is recorded in ingestion_errors.jsonl, including the source, file, location, reason, and original record when available. Records with incorrect field counts or unsupported structures are logged rather than silently discarded. If broken quoting prevents reliable identification of subsequent records, processing of that file stops and the incomplete read is reported. Unreadable XML or JSON documents are logged as file-level failures. Consequently, partial loading counts must be interpreted alongside the error log.
The profiling results are saved in entity_profile.csv, field_profile.csv, and quality_issues.csv. Together with the ingestion log, these outputs provide evidence for the initial inspection and a basis for the subsequent cleaning task.

TASK 2: CLEAN AND STANDARDIZE THE DATA

Task 2 implements a reproducible Python process to clean and standardize the four hospital datasets. The script reads the revised synthetic sources using the Task 1 loaders, maps source-specific field names to common names, and applies documented cleaning rules. Accepted records remain separated by source. The original files are not modified, and global identifier generation and SQL import are reserved for later tasks.
Missing values
The cleaning process distinguishes required information from optional information. Required fields include primary keys, essential relationships, and entity-specific information needed to interpret a record. For example, diagnoses require an admission, patient, physician, ICD-9 code, diagnosis date and time, and diagnosis type. Clinical notes require an authoring physician and a valid note date and time.
Optional information, such as emergency contact details, secondary discharge diagnoses, and prescribed medication summaries, may remain null. Assigned nurse and physician fields are optional in patient records, although these relationships are required for admissions under the project’s cleaning policy.
Documented missing markers—including NA, k.A., 未記録, and NULL—are converted to null. The literal text "None" in allergy and medication fields is preserved because it can express a documented absence. Missing required information causes quarantine rather than the invention of replacement clinical facts. Admission type is also required: a missing or unrecognized source type is quarantined rather than inferred from admission status.
Duplicates
Duplicate detection is performed within each source and entity. Exact repeated records are removed after retaining their first occurrence. Records sharing the same local primary key and identical standardized contents are also treated as duplicate copies. Conflicting records under the same key are quarantined for review.
Patient records with different identifiers but the same insurance number and birth date are treated as possible duplicate entities requiring review. Patients are not merged solely because they share a name. Identical local identifiers from different hospitals are kept separate.
The current run removed 96 exact duplicate copies: 24 from each source. Each source contained eight extra diagnosis records, eight extra clinical notes, and eight extra surgical-procedure records.
Text standardization
Leading and trailing whitespace is removed, and repeated whitespace is collapsed. Synthetic personal-name fields use a title-case display convention outside the Japanese source. Other clinical free text retains its capitalization.
Categorical values are standardized through explicit mappings rather than unrestricted capitalization changes. Original values remain available in the unchanged source files and in quarantined records.
Dates, timestamps, and time zones
Dates are parsed using each source’s documented format and converted to YYYY-MM-DD. Times are standardized to HH:MM:SS. Related dates and times are combined into ISO local timestamps, such as 2025-05-21T08:00:00.
Source B’s dot-separated times are recognized explicitly. Impossible dates, ambiguous layouts, and incomplete date/time pairs are not guessed or automatically repaired. Records containing unresolved date or time problems are quarantined.
None of the sources supplies an explicit time zone. Consequently, the script preserves local wall times without assigning an assumed UTC offset. Chronological comparisons are performed within the same source, and cross-source timestamp comparisons are not treated as reliable.
Numeric values and units
Numeric fields are converted to appropriate integer or decimal types. Fields requiring whole numbers, such as triage priority and procedure duration, reject fractional values.
Broad screening ranges are documented in the cleaning rules. These include temperature between 25 and 45 degrees Celsius, oxygen saturation between 0 and 100, pain level between 0 and 10, and triage priority between 1 and 5. These are project screening assumptions rather than clinical diagnostic thresholds.
Source D’s Fahrenheit temperatures are converted to Celsius using:
Celsius = (Fahrenheit − 32) × 5/9
Converted temperatures are rounded to one decimal place. Invalid optional measurements are replaced with null while retaining the assessment. The run cleared 56 invalid temperature readings, comprising 14 from each source. Missing or invalid required numeric information causes quarantine.
Diagnostic values labelled reference-unit retain that unit because the sources do not provide enough information to infer a physical conversion.
Clinical categories
Explicit mappings standardize source-specific labels. Examples include:
Haupt and 主 → Primary.
Neben and 副 → Secondary.
Notaufnahme, 救急, and EMERGENCY → ED.
Normal, 通常, and LOW → Routine.
Hoch, 緊急, and HIGH → Urgent.
All sources use integer triage priorities from 1 to 5, so these values retain the same scale. Admission types are standardized separately from admission status through these explicit mappings:

- Emergency, Notfall, 緊急 and EMERGENCY map to Emergency.
- Elective, Geplant, 予定 and ELECTIVE map to Elective.

Admission status continues to describe whether an admission is Open or Closed; it is not used as a substitute for type. The cleaner requires an explicit supplied type and never generates a replacement for a missing type. Unknown category labels require review.

Relationships
Supplied foreign-key references are checked against accepted parent records within the same source. Checks cover patients, admissions, professionals, hospital units, orders, examinations, discharge records, and ICD-9 entries.
Additional checks confirm that patient identifiers agree with their admissions, examinations reference orders belonging to the same admission, discharge summaries agree with their discharge records, and unit-stay information matches the referenced hospital unit.
Validation repeats after quarantining records. This prevents a child record from remaining accepted when its required parent has been removed.
Chronology
The script checks that discharge follows admission, unit exit follows entry, examinations do not precede their orders, and radiology reports do not precede their examinations. Linked hospital events must occur within their admission periods. Procedure duration is also checked so that the calculated finish does not extend beyond discharge.
Contradictory timestamps are quarantined rather than moved to an invented date or time.
